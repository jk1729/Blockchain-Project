## 1. Objective

This document formalizes the mapping and verification protocol between simulated adversarial/failure events and the **Phase 19 Production Observability Platform**. During each simulation scenario, telemetry channels—including Structured JSON Logs, Prometheus Metrics, W3C Trace Contexts, Kubernetes Health Probes, and SLO/Alert Rules—must deterministically detect, categorize, and alert on incidents without exposing secrets or degrading core blockchain consensus.

## 3. End-to-End Correlation Verification

During any scenario run:
1. **Simulation ID Correlation**:
   The `simulationId` generated by `SimulationContext` is injected into `RequestContext` and attached to all child log records, e.g.:
   ```json
   {
     "timestamp": "2026-09-18T06:30:00.000Z",
     "level": "warn",
     "component": "SimulationRunner",
     "event": "INJECT_FAULT",
     "simulationId": "sim-1726641000000-a1b2c3d4",
     "scenarioId": "CONSENSUS-001",
     "message": "Injecting conflicting vote from equivocator sim-val-01"
   }
   ```
2. **W3C Distributed Tracing**:
   Each scenario initializes a root span `simulation.run` carrying `traceparent` headers, linking fault-injection child spans to backend database, consensus, and HTTP spans.
3. **Audit Trail Verification**:
   All security scenarios assert that `SecurityAuditLogger` records the actor, target permission, decision (`DENY`), and failure reason, with raw private keys and tokens strictly redacted.

## 4. Alert Lifecycle Validation

Every alert simulated in Phase 20 is validated across three lifecycle phases:
1. **Triggering**: As the fault threshold is exceeded (e.g. pool waiting requests > 0, 50 failed auth requests in 5 seconds), the alert transitions from `INACTIVE` -> `PENDING` -> `FIRING`.
2. **Notification Payload**: The alert record is confirmed to contain `severity`, `summary`, `description`, `runbookUrl`, and relevant metric labels.
3. **Remediation & Clearing**: Once the scenario's recovery hook executes (e.g. pool connections released, peer reconnected, valid validator returned), the metric returns below the threshold and the alert status cleanly transitions back to `RESOLVED` / `INACTIVE`.
